# Speech recognition and playback

Campus OS uses **ElevenLabs Flash v2.5** for streamed speech and **OpenAI GPT Live Transcribe** for recognition through the existing AI Gateway connection. No separate OpenAI or ElevenLabs key or runtime dependency is needed. Explicit speech-model choices and configured Wispr/Deepgram recognition remain in effect. Automatic input recognizes German and English; fixed language choices remain available.

This uses public provider APIs, not ChatGPT's private voice implementation. Sound quality, transcription accuracy and response time still need evaluation on the intended devices and provider account.

## Activation

The deployment owner configures these settings in the hosting dashboard. Agents must not inspect or change private configuration files.

| Setting | Value |
|---|---|
| `AI_GATEWAY_API_KEY` | Existing server-side Gateway key. Requires Gateway speech/streaming-transcription access and credits; audio access rolls out by account. |
| `CAMPUS_AI_SPEECH_MODEL` | Defaults to `elevenlabs/eleven-flash-v2.5`. An explicit model is preserved; `off` disables natural speech. |
| `CAMPUS_AI_SPEECH_STREAMING` | `off` disables streaming playback while retaining buffered speech. Streaming is enabled for the default Flash v2.5 model. |
| `WISPR_FLOW_API_KEY` | Wispr organization API key, server-side only. Requires Wispr-approved Voice Interface API access; a desktop Flow subscription alone does not grant this access. |
| `DEEPGRAM_API_KEY` | A Deepgram project key with Member permission or higher, required by `/v1/auth/grant`. Keep it server-side. |
| `CAMPUS_STT_PROVIDER` | `gateway`, `wispr`, `deepgram` or `browser`. If unset: configured Wispr, then Deepgram, then Gateway, otherwise browser recognition. `gateway` selects OpenAI live transcription. |
| `CAMPUS_STT_REGION` | `eu` (default) or `global`. EU uses `api.eu.deepgram.com`. |

Request Wispr access through its [developer portal](https://platform.wisprflow.ai) and [quickstart](https://api-docs.wisprflow.ai/quickstart). Enable the institution's AI provider in Admin / AI & knowledge and redeploy after setting hosting variables. External recognition is billed by its service. No new runtime dependencies are installed.

Settings / Assistant identifies the configured recognition system. While the wake phrase is enabled, audio streams to the selected service, including while waiting for the wake phrase. Turning listening off closes capture and releases the microphone. HTTPS (or localhost) and microphone permission are required. Native browser recognition is the fallback when supported; the app shows a notice when falling back.

## Audio and authentication

- `POST /api/speech/playback-session` and `/api/speech/recognition-session` obtain single-use, model-bound Gateway grants that expire after 60 seconds if unused. They require sign-in, same-origin requests, the institution's enabled AI, and separate per-user/institution quotas. Speech output also honors the institution's speech switch. The deployment key never reaches the browser. Grant responses are `no-store`; tokens stay in memory and use WebSocket authentication subprotocols rather than URL parameters.
- Playback sends speakable text through Gateway's documented speech-stream envelope. ElevenLabs returns mono 24 kHz signed 16-bit PCM, scheduled on one playback clock as it arrives. The connection opens while the chat model prepares its answer, and later sentences use the same connection and voice. Streaming startup failures fall back to buffered speech with the same model before device fallback; interrupted audio reports failure and can be replayed. Buffers and timeouts are bounded, and cancellation closes the socket and stops scheduled sound.
- OpenAI capture uses a 24 kHz AudioContext and 50 ms PCM AudioWorklet packets. Live deltas and corrected partials update the transcript; only finalized segments become saved captions. Capture starts before the grant request, stays open through pauses and transcription-connection changes, and queues up to ten seconds of audio while connecting. Turns normally commit after about 2.2 seconds without speech or new transcript words, and about four seconds after unfinished connectors or filler words. This is a local text-and-energy heuristic, not OpenAI semantic VAD. Medium transcription delay favors more stable text over the former low-delay setting. Conversation and wake-word actions wait for the final corrected transcript and any queued speech; a measured pause is not counted twice. Send/Space drains the current turn without releasing the microphone. Manual stop flushes audio before finalization; abort, mute and errors release capture immediately. Transcription connections rotate after 90 seconds without reacquiring the microphone; a logical session is bounded to 128 turns. Unsupported capture rates and unavailable Gateway recognition fall back to native recognition where available, with a notice.
- The current Gateway OpenAI streaming adapter supports fixed language and configurable transcription delay, but does not forward vocabulary/context hints. Automatic mode leaves language unrestricted. Lecture-specific keyterms remain a Deepgram feature. Audio and tokens are not stored by Campus OS; provider processing and retention terms apply. The adapter does not expose the Realtime semantic-VAD settings described in OpenAI's voice-agent documentation. Recognition connections reopen after committed phrases while the same microphone keeps capturing into a bounded memory queue. Test phrase boundaries, thinking pauses, quiet speech and interruptions in real use.

- Microphone capture requests the browser's established WebRTC echo cancellation, noise suppression, automatic gain control and mono audio. Actual audio processing depends on browser/hardware support. Deepgram also handles background noise in its recognition model. There is no extra custom denoising model or speaker identification.
- Bluetooth headphones play everything in muffled call quality while their microphone records. When the default microphone is a headset and the computer has its own, Deepgram and Wispr record from the computer's microphone, so the headphones keep their full sound (public/js/features/microphone.js). When the headset is the only microphone, or the browser's recogniser is used, the voice conversation releases the microphone while Campus talks; tap or press Space to interrupt.
- `POST /api/speech/recognition-session` requires a signed-in user, validates language and honors the institution's AI-off setting. Grants are limited per user/institution: 24 per minute for Wispr, 20 for Deepgram or Gateway. Phones reopen capture after each answer.
- Wispr requests go through `deps.ai.recognitionSession`. The server exchanges its organization key for a 120-second grant tied to the institution/user. The browser uses Wispr's documented client WebSocket authentication, including the temporary token in the URL and auth message. Capture uses a 16 kHz AudioContext and local AudioWorklet with fixed 50 ms little-endian int16 PCM packets. Unsupported capture rates fall back to browser recognition.
- Wispr receives app identity and a small vocabulary list (campus terms, the user's programme and assistant nickname), without chat history, screenshots or private documents. A local energy detector commits after speech followed by about one second of quiet; manual stop also flushes and commits. Very quiet speech may be missed and loud noise may count as speech. Only final transcripts are emitted, since Wispr can rewrite partial text. It does not provide word-by-word live captions here. Idle streams rotate after 90 seconds and finalization is bounded to eight seconds.
- Deepgram calls go through `deps.ai.recognitionSession`. Only the server reads the project key. It exchanges it for a 30-second temporary token; the browser holds that token only in memory and uses the WebSocket authentication subprotocol. All grant responses are `no-store`.
- Microphone permission is obtained before requesting the temporary token. Audio streams as MediaRecorder container chunks directly to the selected Deepgram region. Campus OS stores neither the audio nor the token. Existing chat/caption text follows its existing storage behavior. `mip_opt_out=true` is sent to Deepgram; its account terms and retention controls still apply.
- The Deepgram client rotates streams after two minutes and sends the same vocabulary as recognition keyterms. Both adapters flush the final audio on stop, release tracks on abort/error, bound buffered audio and reuse existing reconnect/turn-taking behavior. Campus OS does not store recognition audio or grants; existing chat/caption storage and provider retention terms apply.

## Best recognition without waiting for Wispr

Wispr Flow needs approved API access. **Deepgram Nova-3 does not**: create a Deepgram project key (self-serve, free starting credit), set `DEEPGRAM_API_KEY` and leave `CAMPUS_STT_PROVIDER` unset, and Campus uses it automatically for dictation, the wake phrase, conversations and the live lecture. It decodes German and English together, streams words as they are spoken, and the app asks the browser for echo cancellation, noise suppression and gain control.

For lectures, recognition also learns the lecture's vocabulary. When the lecturer opens a live lecture, each recognition session carries its id (`live_session`), and the server sends Deepgram keyterms built by `src/modules/live/vocabulary.js`: the lecture and course titles, the topic names, and terms that stand out in the uploaded notes (acronyms, names, capitalised phrases, repeated technical words), up to 100. Only the lecture's own lecturer receives them. Text is mined from documents (PDF, Word, PowerPoint, text); a photo of a slide has no text to mine. The stream rotates every two minutes, so notes added mid-lecture are picked up at the next rotation.

What this does not do: it does not classify non-speech sounds (applause, a door), identify who is speaking, or remove noise beyond what the browser and Deepgram do. In a large room, accuracy depends mostly on the microphone: a lapel or headset microphone on the lecturer, or a USB conference microphone, beats a laptop microphone at the back. Measure it in the real room before promising accuracy.

## Playback

Generated audio receives bounded per-clip loudness correction and a compressor to reduce volume jumps. Saved volume settings remain in effect. Device playback keeps one voice per language throughout an answer and retries a dropped sentence once. Natural speech requests have bounded timeouts and one retry before device fallback. Supported phones request playback audio routing while the microphone is paused. Campus's gaze stays centered while speaking.

Streaming PCM preserves the provider's level rather than applying gain separately to tiny chunks. The same master volume and peak compressor control playback. Settings / Assistant exposes volume, speaking speed, samples, a Stop sample button and the configured voice service. Conversations have a live volume slider and Replay answer button. Zero volume stays muted. Turning the microphone off releases capture even during an answer.

For deployments explicitly retaining `openai/tts-1` or `openai/tts-1-hd`, the catalog includes only their supported voices. Realtime-only names such as Coral cannot reach those legacy endpoints. These older speech models are deprecated by OpenAI; use the default ElevenLabs model for new deployments.

The new default Flash v2.5 is billed through Gateway and has different pricing from the former `tts-1` default. An explicit `CAMPUS_AI_SPEECH_MODEL` remains unchanged. Check account access and pricing before evaluating a production rollout; no live paid request was made during automated verification.

## Live voice (GPT-Live)

On computers, the voice conversation uses OpenAI **GPT-Live** (`openai/gpt-live-1`) through the AI Gateway when the account has it. One WebSocket carries the microphone and Campus's voice. The model hears the person while it talks and decides itself when they have finished, so there is no separate recognise, answer and speak chain: replies start as soon as the person stops, pauses to think are waited out, and talking over Campus interrupts it.

- `POST /api/assistant/live` (signed-in users, institution AI on, natural voices allowed) mints a single-use pass with `POST https://ai-gateway.vercel.sh/v1/realtime/client-secrets` (`routeKind: live`) and returns it with the conversation's instructions: the assistant's rules (`livePrompt` in `src/ai/prompts.js`) and the user's CONTEXT. The gateway key never reaches the browser. Six passes per user per minute.
- The browser (`public/js/features/live.js`) connects to `wss://ai-gateway.vercel.sh/v1/live/sessions`, sends `session.start` (client delegation, `store: false`, 24 kHz PCM), streams the microphone in 50 ms packets after `session.started`, and plays `session.output_audio.delta` on the natural-voice output (`createLivePlayer` in `speaker.js`). Bluetooth handling (`microphone.js`) applies.
- Anything that needs Campus OS (timetable, courses, university pages, web search, actions in the app) is delegated. The browser sends the words of that turn, and what Campus said just before them (`live_context`), to `POST /api/assistant/messages` in voice mode, so permissions, sources and actions work as in chat and the exchange is saved in the thread. The answer goes back with `session.commentary.append` for GPT-Live to say. GPT-Live's own small talk is not saved.
- If live voice cannot start (no model access, connection refused), the standard conversation opens instead and live voice rests for ten minutes; a refused pass also rests it on the server. Phones keep the standard conversation for now.
- **Cost.** GPT-Live is billed per second of open conversation, including silence and mute: $3 per hour at the current list price, plus the assistant calls for delegated questions. The conversation ends itself after two quiet minutes, and closing it sends `session.close`.
- When a live conversation stops for any reason other than being closed, the browser reports the close code, the gateway's error and which events arrived to `POST /api/assistant/live/trouble`, which writes one line to the server log (`Campus OS live voice ended:`). No words or audio are sent. Read it with `vercel logs`.
- `CAMPUS_AI_LIVE_MODEL` sets the model (default `openai/gpt-live-1`); `off` turns live voice off. The Admin switch for natural voices also turns it off.

## Verify after activation

1. In Settings / Assistant, select Automatic voice input. Allow the microphone.
2. Dictate “Ich brauche my timetable für morgen” and check the live text in both languages.
3. Test the wake phrase, a conversation with a 1.5-second mid-sentence pause, a longer pause after "because" or "und", quieter speech, an interruption, Send/Space and stopping listening. Confirm the browser's microphone indicator switches off when stopped.
4. Test with ordinary room noise and headphones/speakers. Compare recognition with the browser fallback before making accuracy or latency claims.

With Wispr, pause to finish each phrase. Test names, corrections and quiet speech as well as the bilingual examples. Check short and long replies on the intended speakers/headphones and phone. Automated tests simulate provider and audio events; live approved accounts, a microphone and output device are still needed to measure speed, accuracy and loudness.
